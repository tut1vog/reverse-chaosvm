**Notes**: two caveats recorded but not blocking acceptance:

1. **Non-idempotent `live_run` fields**: re-running the script produces a different `live_run.vdata` and `live_run.ciphertext_hex` (sha256 mismatch post-rerun). All stable fields (`xtea_key_hex`, `encrypt_entry_pc`, `output_alphabet`, `har_reference.*`, `plaintext_blocks` structure) are stable. The variability is rooted in jsdom's non-deterministic object enumeration order and, probably, an internal salt — see VDATA-PIPELINE.md §8 open question 3. Acceptable for a dynamic research artifact; 43.2 will freeze one run as a committed fixture if we proceed.

2. **Custom alphabet length = 65, not 64**: the stored `output_alphabet` is `GV5yc1_twaSpHPOE7R3jv9fqC2L-0TxMi4FuolBAbQeIgJU*XzZKWkDNh6n8dsrmY` at length 65 with `Y` at index 64. The script's `customBase64Decode` iterates `i < alphabet.length` (so maps Y→64), and by arithmetic coincidence `(64<<6)|64 = 0x1040` — which produces the `10 40` trailer bytes when `YY` appears as the last two characters of a 4-char base64 group. The decoder is internally consistent and byte-identical against the HAR reference, but the 65-char alphabet is suspicious (real 6-bit base64 has 64 values). Flagged as a 43.3 re-verification item: re-read bytecode pc 16932 directly to confirm whether Tencent\'s alphabet really is 65 chars or whether one character is duplicated / extraneous.

**Plan revision triggered — pause for user review**: 43.1's biggest finding wasn't the XTEA key — it was that the **plaintext being encrypted is not the verify POST body**. Decrypting either the jsdom ciphertext or the HAR reference with the recovered key produces 112 bytes shaped as 8 `key=value` pairs joined by `&`, structurally identical but with content that differs between jsdom and real Chrome (jsdom has parens/apostrophes/spaces; HAR has lots of `k`s and digits). The 112-byte plaintext is a **JS-environment fingerprint** computed inside vm-slide's `proxyXHR` body from `typeof`, property enumeration, and object stringification — NOT the POST body. Per-run byte order varies even with identical input.

This reshapes Phase 43's definition of "byte-identical vData generator" because the cipher pipeline (XTEA + key + LE packing + trailer + custom base64) is now fully byte-identical reproducible, but the plaintext *content* requires either decompiling the proxyXHR fingerprint build (new task, ~2-4 sessions) or accepting the generator as a pure re-encoder that consumes a pre-computed plaintext buffer. No writes to `tools/vdata-generator/`, `tools/scraper/vdata-harness.js`, `targets/`, or `sample/`.

**Notes**: the **biggest finding is a correction to 43.1**: the "constant 2-byte trailer `10 40`" claim was a phantom. It was the result of decoding the `YY` base64 padding chars as raw 6-bit values (`(64<<6)|64 = 0x1040`) rather than recognizing them as standard base64 padding. The real cipher pipeline is 14 × 8-byte XTEA blocks (= **112 bytes flat, no trailer**) → 152 chars of standard base64 with the 65-char alphabet where index 64 is the padding char. Every vData ends in `YY` because 112 bytes = 37·3 + 1, so the last group needs 2 padding chars. This invalidates the "trailer" framing in `VDATA-PIPELINE.md` (now corrected) and significantly simplifies 43.3's encoder — it's just XTEA + standard base64 with a custom alphabet, no special trailer logic. Also unexpectedly: the existing `vdata-dynamic-trace.js` encoder is wrong on the trailing 2 chars (re-encoding HAR ciphertext via its `customBase64Encode` produces `...5RsJR4VG` instead of HAR's `...5RsJRiYY`); 43.3 will supersede it. The encoder bytecode location (pcs 17084..17418, including `isNaN`-guarded padding immediates) is now pinned, giving 43.3 a free down-payment.

**Plan changes**: 43.2 → done. 43.3 → in-progress as the next dispatch. Phase 43 description rewritten in `plan.md` to remove the obsolete "10 40 trailer" wording.
