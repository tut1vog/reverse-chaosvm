## 39.1: Implement vm-slide decoder + disassembler

**Outcome**: passed

**What was done**: Built two runnable tools under `research/vm-slide-stack-vm/`:
- **`decoder.js`** — parses `sample/vm_slide.js` with acorn, walks the AST to find the inner `__TENCENT_CHAOS_VM` function declaration, extracts the `Q = [...]` dispatch-table ArrayExpression, records each handler's source + statically-inferred operand count (counting `m[g++]` MemberExpression nodes in each handler body), preserves sparse-array holes as `null`, extracts the inline bytecode ArrayExpression from the outer invocation `__TENCENT_CHAOS_VM(0, [...], window)`, and writes `output/vm-slide/dispatch-table.json` + `output/vm-slide/bytecode.json`.
- **`disassembler.js`** — loads the two JSON artifacts, walks the bytecode linearly starting from PC 0, reads opcode + operand-count bytes per instruction, emits column-aligned text with placeholder `OP_NN` names, gracefully halts on dispatch-table holes with a `WARN` marker to stderr, and writes `output/vm-slide/disassembly.txt`.

Both are CommonJS CLIs with no external deps beyond acorn. Output versioning follows `.claude/rules/output-versioning.md` (stable filenames under `output/vm-slide/`, no timestamps). Default inputs/outputs are the committed paths; `--input`/`--dispatch`/`--bytecode` flags override.

**Key findings for downstream tracks**:

1. **Dispatch-table size is 53, not ~36.** `project-brief.md` §Stream B Track 1 estimated ~36 opcodes; the actual count is substantially higher. Update the brief when 39.3 finalizes the architecture doc.

2. **Bytecode length is 24,273, much larger than the director's pre-task ~4K estimate.** The bytecode carries significant data — possibly method name strings encoded as per-character `OP_0A` pushes (`function(){n[n.length-1]+=String.fromCharCode(m[g++])}` is handler 10 per the file's prefix), literal tables, and XTEA state.

3. **Observed operand counts: [0, 1, 2, 6]** — the **`6` is surprising and worth investigating** in 39.3. Could be a legitimate composite handler (e.g. a 6-arg constructor call), or a static-count false positive if a handler contains a branch with multiple `m[g++]` reads (the static count would then double-count dynamically-exclusive reads). 39.3 should classify each of the handlers with operandCount≥2 and either confirm or correct the static count.

4. **XTEA delta `0x9E3779B9` (2654435769) appears exactly 2 times in the bytecode** — strong signal that vm-slide carries its own XTEA-style round function, sharing crypto machinery with the register-machine tdc.js family. This connects the `vm-slide-stack-vm`, `eks-payload`, and `key-mod` research tracks: the stack VM may be running the XTEA schedule that produces or consumes eks. Flag for future cross-track work.

5. **Linear walk is fundamentally insufficient for complete disassembly.** The disassembler halts at pc=512 after decoding only 312 instructions — that's only ~2% of the 24,273-byte bytecode. The halt is legitimate (opcode 65 is a genuine dispatch-table hole), which means the VM's bytecode stream interleaves code with data regions, OR control-flow (`OP_06` appears to be the JMP-style handler judging by its operand pattern: `OP_06 1568`, `OP_06 42`, `OP_06 289` jumping to far addresses) is essential for disassembly correctness. **39.3 will need to address this**, either via control-flow tracing starting from the entry point or by identifying data regions explicitly. For 39.1's purposes, the partial disassembly is the expected output and gets pinned by 39.2's tests.

6. **One bytecode element is a float literal (`0.5`).** The decoder handles this correctly because it walks acorn Literal nodes, which carry numeric values untouched. Any future consumer that assumes the bytecode is `Int32Array`-compatible will break.
