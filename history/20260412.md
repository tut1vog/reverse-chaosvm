**CRITICAL FINDING — handler 58 `FUNC_CREATE` is variable-width**: the subagent resolved the operand-count-6 mystery by reading handler 58's source. The handler is:

```js
function(){
  for(var K=m[g++],p=[],A=m[g++],C=m[g++],Q=[],B=0;B<A;B++)p[m[g++]]=n[m[g++]];
  for(B=0;B<C;B++)Q[B]=m[g++];
  n.push(function w(){
    var A=p.slice(0);
    A[0]=[this],A[1]=[arguments],A[2]=[w];
    for(var C=0;C<Q.length&&C<arguments.length;C++)0<Q[C]&&(A[Q[C]]=[arguments[C]]);
    return __TENCENT_CHAOS_VM(K,m,U,A,E,F,Y,c);
  });
}
```

Runtime byte width is `3 + 2·A + C` where A and C are operand values, NOT 6. The decoder's static `operandCount: 6` is a **lexical count** of `m[g++]` syntactic occurrences — `K`, `A`, `C` in the outer declarations (3) + `p[m[g++]]=n[m[g++]]` in loop 1 (2) + `Q[B]=m[g++]` in loop 2 (1) = 6. But at runtime, the `m[g++]` expressions inside the two `for` loops execute multiple times each (loop 1 runs A times with 2 reads per iteration, loop 2 runs C times with 1 read per iteration).

Three implications captured for Phase 40:
1. **The 39.1 linear disassembler mis-parses every `FUNC_CREATE` site**, which is likely why it halts at pc=512 on "opcode 65" — the walker is probably mid-stream through a mis-parsed FUNC_CREATE and the "65" is actually data from inside the variable-width operand region. This may mean the decoded disassembly is substantially wrong, not merely incomplete. Tests pin it byte-for-byte so regressions are detectable, but "correct" and "pinned" are not the same here.
2. **Phase 40 task 40.1 must handle `FUNC_CREATE` FIRST**, before any control-flow tracing can work. The walker upgrade needs to recognize variable-width opcodes and read operand prefixes to determine real byte width. Plan updated accordingly — task 40.1's description now explicitly mentions FUNC_CREATE + the `3 + 2·A + C` formula.
3. **`FUNC_CREATE` instantiates nested VM invocations** — the handler constructs a closure that, when called, executes `__TENCENT_CHAOS_VM(K, m, U, A, E, F, Y, c)` with a new entry PC `K`, a fresh locals array `A` seeded from captures `p`, and `arguments` / `this` injected. This is how vm-slide does closures and first-class functions: each callable is a sub-program in the same bytecode at a different entry PC. Also resolves a standing question about what extra arguments `F`, `Y`, `c` are for — they're forwarded to nested invocations as helper/env slots supplied by the outer caller.

**Other classification highlights from the subagent's report**:
- **Opcodes 24 (STORE_REF) and 36 (STORE_LOCAL_REF) do not pop** — they write through TOS-1 but leave both operands in place. Subsequent `POP` (opcode 5) is implied.
- **Opcode 60 (JUMP_IF_TRUE) does not pop the test value** — consistent with `&&` / `||` short-circuit semantics where the test value becomes the expression result.
- **Opcode 15 (ITER_NEXT)** mutates TOS via `.shift()` on the TOS array, storing iterator state in the array object itself (no separate iterator register).
- **Operand stack init `n = [[this],[{}]]`** — both initial cells are single-element arrays because local slots are always 1-cell arrays, enabling in-place mutation via ref-pair handlers (MAKE_LOCAL_REF / LOAD_LOCAL_REF / STORE_LOCAL_REF).
- **Opcode 66 (CALL_GLOBAL)** applies functions with `this = U` (i.e. `window`), whereas opcode 2 (METHOD_CALL) uses the receiver from the ref pair — two distinct "call" modes intentionally separated.

## 40.6: Cross-track investigation — does vm-slide run XTEA?

**Outcome**: passed — **Outcome 1: CONFIRMED classical XTEA, both encrypt and decrypt**

**What was done**: Investigation using the 40.1 walker's full-coverage disassembly to locate the two `0x9E3779B9` occurrences in the vm-slide bytecode and confirm (with full structural evidence) that they are part of classical XTEA cipher round implementations.

**Concrete findings**:
- Delta constant `2654435769` (= `0x9E3779B9`) appears at bytecode indices **`15353`** and **`15531`**. Each is the operand of a preceding `OP_08 PUSH_K` instruction at PCs `15352` and `15530`.
- **Encrypt function**: entry PC **`15241`**, created by a `FUNC_CREATE` at PC `15404` (`OP_58 15241 0 2 3 4`). Loop bound is `sum == 84941944608` (= 32·delta). Backward jump `15377 → 15284` closes the 32-round loop. Uses `ADD` for `sum += delta` and `v += ...`.
- **Decrypt function**: entry PC **`15416`**, created by a `FUNC_CREATE` at PC `15579` (`OP_58 15416 0 2 3 4`). Same skeleton but with `SUB` instead of `ADD` — the classical XTEA decrypt inverse. Loop bound `sum == 84941944608`, backward jump `15552 → 15459`.
- **Both closures are instantiated by an outer factory** at entry PC **`15220`**, which is itself created by a `FUNC_CREATE 15220 0 3 3 4 5` near PC `16835` from within a CommonJS-style `__esModule` bootstrap routine. The factory takes 3 arguments (local slots 3, 4, 5). One of these is almost certainly the key material.
- **All XTEA structural features verified in the disassembly**:
  - `PUSH_K 4; SHL` — shift left by 4 for `(v << 4)`
  - `PUSH_K 5; USHR` — unsigned shift right by 5 for `(v >>> 5)`
  - `XOR` — combine shifted halves
  - `LOAD_LOCAL` + `ADD` — `v += shifted + v`
  - `PUSH_K 3; AND` — key index `sum & 3`
  - `PUSH_K 11; USHR; PUSH_K 3; AND` — second key index `(sum >>> 11) & 3`
  - `MAKE_LOCAL_REF 4` + `MAKE_LOCAL_PAIR; DEREF` — key array read
  - `PUSH_K 2654435769; ADD` — `sum += delta`
  - Backward `OP_06 JUMP` with target before current PC — 32-round loop

**Critical observations**:

1. **This is classical XTEA, NOT the register-VM's modified XTEA.** The register VM uses a modified variant with per-template STATE_A key derivation and `keyModConstants`. vm-slide's round function is the vanilla Needham/Wheeler formulation from XTEA's original 1997 paper, taking the key as a plain argument. **The `key-mod/` research track's findings do NOT apply to vm-slide** — vm-slide takes its key from somewhere else entirely (likely session state, a caller-supplied argument, or a server response).

2. **Both encrypt AND decrypt are present.** The register VM only needs encrypt (token generation). vm-slide having both strongly suggests it participates in a **round-trip**: it may decrypt something the server sends (candidate: the `eks` token, matching Known Unknown #3) and encrypt something before returning it (candidate: the verify-POST body or a session token). This is the strongest structural hint so far that `eks` decryption happens inside vm-slide rather than being opaque server-baked state.

3. **Blocking limitation for caller identification**: the encrypt/decrypt closures are stored via `STORE_LOCAL_REF` into outer locals 6 and 7 and then exposed through module exports (the surrounding code builds `__esModule`). Without dynamic instrumentation or a full module-export-name trace, static analysis cannot say "encrypt is called with eks as input". The correct follow-up is either runtime hooking of `__TENCENT_CHAOS_VM` at the encrypt/decrypt entries, or extending static analysis to trace the module-export object and match property names to the stored closures. This is a natural handoff to the `captcha-orchestrator` or `eks-payload` research tracks rather than something for Phase 40 to resolve.

4. **Unusual loop-bound encoding**: rather than a round counter decrementing from 32, the VM compares `sum` directly against `32*delta = 84941944608`. This is the exact formulation some XTEA reference implementations use; it cleanly explains both the literal `84941944608` in the disassembly and the extra `PUSH_K delta; ADD` per round.

5. **Inlined bytecode layout surprise**: the encrypt and decrypt functions are consecutive in the bytecode stream with a JUMP 15577 skipping across the encrypt body — a compilation artifact of how this VM's compiler linearises nested functions. Both function bodies are inlined sequentially and jumped over during normal execution, only reached when invoked as closures via the FUNC_CREATE entry PCs. This is a clever (or just pragmatic) use of the bytecode's flat address space.

**Deliverables**:
- `research/vm-slide-stack-vm/xtea-hunt.js` — new standalone analysis script that reads `output/vm-slide/bytecode.json`, locates the two delta occurrences, identifies their containing function entries, and prints semantically-annotated disassembly windows around each. Reproducible record of the investigation.
- `docs/VM_SLIDE_ARCHITECTURE.md` — single narrow edit to the "Unresolved findings" section replacing the XTEA bullet with the confirmed finding (and pointer to the xtea-hunt script). Everything else in the doc is untouched.

**Verification** (director independent):
- `node research/vm-slide-stack-vm/xtea-hunt.js` — runs cleanly, stdout shows delta indices `[15353, 15531]`, function entries `15241` (encrypt) and `15416` (decrypt), 101 FUNC_CREATE entries total, annotated disassembly windows around both deltas showing the full round structure.
- `grep '15241\|15416\|15220\|XTEA'` in `docs/VM_SLIDE_ARCHITECTURE.md` — new bullet is present at line 184 with all the key PCs and the "confirmed classical XTEA" framing.
- `git diff --stat docs/VM_SLIDE_ARCHITECTURE.md` — 1 insertion / 1 deletion (single-bullet replacement). Surgical.

**Notes**: This is the single most significant finding of Phase 40 and possibly the entire session. It resolves one of the highest-value open questions from the 39.3 architecture doc (the XTEA delta mystery), confirms the cross-track connection between `vm-slide-stack-vm` and the `eks-payload` / `key-mod` / `captcha-orchestrator` tracks, and establishes that vm-slide is architecturally much more than a peripheral VM — it's running production-grade crypto on values that matter.
